# StudentConnect — этап 9

Учебный проект для студентов колледжа МИЭТ. Реализованы регистрация, вход и выход, подтверждение электронной почты, серверные сессии, редактирование профиля, загрузка аватара, категории и конкретные интересы. Пользователь может создать интерес, увидеть похожие варианты и пожаловаться на неподходящее название. Главная страница после входа показывает других студентов с поиском, фильтрами и сортировкой по общим интересам.

Мероприятия, заявки, управление составом и уведомления внутри раздела мероприятий реализованы. Личные сообщения, история диалогов, непрочитанные и запрос телефона с одобрением/отзывом доступны. Работают общий колокольчик уведомлений, лента со свайпами и отчёты об ошибках. Для размещения подготовлен единый production-сервер; текущий статус и условия — в DEPLOY.md.

## Обновление уже запущенного проекта

Подробная инструкция для Windows — в `UPDATE.md`.

1. Остановите приложение в терминале сочетанием Ctrl+C. Docker Desktop оставьте запущенным.
2. Скопируйте содержимое папки `studentconnect` из нового архива в существующую папку проекта с заменой файлов. Сохраните свои `.env` и `compose.yaml`, если меняли настройки базы. В архиве нет файлов `.env`, поэтому они не заменятся. Не создавайте вложенную папку `studentconnect/studentconnect`.
3. В терминале VS Code из корня проекта выполните команды по одной:

```powershell
npm.cmd ci
npm.cmd run db:generate
docker compose up -d --wait
npm.cmd run db:migrate
npm.cmd run db:seed
npm.cmd run dev
```

Откройте **http://localhost:5173**. В Linux/macOS используйте `npm` вместо `npm.cmd`.

Вторая миграция добавляет поля и таблицы, не удаляя записи первого этапа. Курс существующих пользователей переносится из учебной группы. Не выполняйте `prisma migrate reset` или `docker compose down -v`: эти команды удаляют данные.

## Проверка регистрации и почты локально

По умолчанию действует **тестовая почта** (`MAIL_MODE=console`). Настоящее письмо не отправляется — это явно указано на странице подтверждения.

1. Нажмите «Присоединиться». Введите имя, фамилию, группу, курс, почту и пароль от 10 символов с буквой и цифрой.
2. На втором шаге выберите хотя бы один конкретный интерес. Фото, псевдоним, телефон и описание необязательны.
3. Нажмите «Создать аккаунт».
4. В работающем терминале VS Code найдите блок `[ТЕСТОВАЯ ПОЧТА — реальное письмо НЕ отправлено]` и строку `Подтвердить:`. Откройте **всю ссылку**, включая `#token=...`. В VS Code обычно достаточно Ctrl+щелчка по ссылке.
5. На странице нажмите «Подтвердить почту». Профиль становится доступным после подтверждения.
6. Перейдите в профиль через аватар справа сверху. Измените поля и нажмите «Сохранить изменения».
7. Нажмите «Как видят другие»: в публичном ответе сервера отсутствуют почта и телефон.
8. Выйдите и снова войдите. Для второго тестового пользователя откройте другой браузер или окно инкогнито; обычные вкладки одного браузера используют общую сессию.

Ссылка действует 24 часа и может использоваться один раз. Повторная отправка доступна раз в минуту. Если SMTP не сработал, аккаунт сохраняется и можно запросить письмо повторно. Закрытие браузера не завершает сессию: она действует до 7 дней или до выхода. Сессия хранится в PostgreSQL, поэтому перезапуск Node.js не сбрасывает вход.

### Настоящие письма

Для бесплатного Render используйте HTTPS API Brevo по DEPLOY.md. Ниже — сохранённый вариант SMTP для локальной проверки и хостингов, разрешающих SMTP-порты.

В `apps/api/.env` задайте параметры своего SMTP-провайдера:

```dotenv
MAIL_MODE=smtp
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=your-user
SMTP_PASSWORD=your-password
MAIL_FROM=StudentConnect <your-verified-sender@example.com>
```

Перезапустите backend. Порт 465 использует TLS сразу, остальные порты требуют STARTTLS. Используйте реальные параметры провайдера и подтверждённый адрес отправителя. SMTP-пароль не помещайте в frontend или GitHub. Реальная доставка писем при подготовке проекта не проверялась — нужен ваш SMTP-аккаунт. В production запуск с `MAIL_MODE=console` запрещён.

## Интересы и профили

- Имя, фамилия, группа, курс, псевдоним, описание, аватар и интересы доступны авторизованным студентам с подтверждённой почтой.
- Email возвращается только владельцу через `/api/auth/session` и редактирование своего профиля. Телефон также доступен конкретному собеседнику через детали своего чата после одобрения владельцем. Изменять чужой профиль через API нельзя: сервер берёт идентификатор владельца из сессии.
- Фото принимается как JPEG/PNG/WebP до 1 МБ. Сервер декодирует изображение, ограничивает число пикселей, убирает метаданные и сохраняет WebP размером до 256×256 прямо в БД. Внешние URL и SVG не принимаются.
- Обязателен минимум один конкретный интерес, максимум 20. Самостоятельное создание интересов доступно после подтверждения почты в редакторе профиля.
- Для нового интереса выберите категорию, введите название в поиск, проверьте похожие варианты и нажмите «Добавить». Например, `CS2`, `Counter-Strike 2` и `КС2` объединяются. Действуют нормализация, набор алиасов и уникальный индекс, а не распознавание всех возможных синонимов.
- Фильтр запрещённых слов — базовый словарь с нормализацией; он не заменяет модерацию и может ошибаться. Жалобы хранятся в `InterestReport`. Страница модератора пока не реализована. Разработчик может просмотреть записи через Prisma Studio: из `apps/api` выполнить `npx.cmd prisma studio`.
- Если другая вкладка вошла в другой аккаунт или сессия истекла, обновите страницу перед сохранением: для изменений требуется актуальный CSRF-токен.

Для бесплатной демоверсии подготовлен единый Node.js-сервис Render (интерфейс + API + чат), Neon PostgreSQL и HTTPS-почта Brevo. Пошаговые настройки и ограничения — в [DEPLOY.md](DEPLOY.md). Публичный запуск: NODE_ENV=production, SERVE_WEB=1, MAIL_MODE=brevo, COOKIE_SAME_SITE=lax, TRUST_PROXY=1 за одним Render-прокси. WEB_ORIGIN берётся из RENDER_EXTERNAL_URL, если явно не задан. Облачная база отдельная: локальные аккаунты/переписка не копируются автоматически и не удаляются. В первом облачном показе создаются новые аккаунты с настоящим подтверждением почты. Готовность к публикации не означает уже выполненное размещение; окончательный адрес и доставку писем подтверждаем после настройки аккаунтов.

## Поиск студентов (этап 3)

После входа и подтверждения почты главная страница — каталог других студентов. Показываются только профили колледжа с подтверждённой почтой и минимум одним конкретным интересом; собственная карточка исключена. Если у владельца сессии нет интересов, поиск предлагает заполнить профиль.

В карточке есть аватар или инициалы, имя, фамилия, псевдоним, группа, курс, описание, интересы и число совпадений. Общие интересы выделены цветом. Кнопка «Профиль» открывает публичный профиль. «Написать» открывает личный диалог. Почта и телефон не возвращаются в списке даже при подмене query-параметров.

Поиск по имени/фамилии (в обоих порядках) и псевдониму не зависит от регистра. Префикс @ допустим. Для имени и группы нажмите «Найти студентов» или Enter. Курс, категория, конкретные интересы и сортировка применяются сразу. Все разные фильтры сочетаются через И. При выборе нескольких конкретных интересов достаточно любого из них (ИЛИ). Все интересы выбранных карточек остаются видны независимо от фильтра.

По умолчанию сортировка — по числу общих интересов с владельцем сессии, затем по фамилии/имени/id. Доступна отдельная сортировка по фамилии. Подсчёт совпадений и сортировка происходят в PostgreSQL до пагинации. Размер страницы — 12 по умолчанию, API допускает максимум 24. Фильтры и страница хранятся в URL, работают обновление и возврат браузера. Нагрузка и многопользовательские гонки полноценного PostgreSQL отдельно не проверялись.

Параметры `GET /api/people`: `q` (до 60 символов), `group` (до 24 символов), `course` (1–6), `category` (id), `interests` (до 20 id через запятую), `sort=matches|name`, `page` (от 1), `limit` (1–24). Ответ: `users`, `total`, `page`, `limit`; у каждой карточки есть `commonCount` и `commonInterests`. Все SQL-параметры передаются через Prisma.sql; сортировка выбирается только из серверных вариантов. Третий этап не добавлял миграций. Для четвёртого этапа обязательно примените новую миграцию мероприятий командой db:migrate.

Для ручной проверки создайте два-три своих аккаунта в разных браузерных сессиях, подтвердите почту и задайте пересекающиеся интересы. Проверьте порядок карточек, фильтры, публичный профиль и отсутствие собственного аккаунта. В пустую базу фальшивые профили и аккаунты с общим паролем не добавляются.

## Мероприятия (этап 4)

На странице «Мероприятия» доступны предстоящие встречи, «Я организую», «Я участвую» и прошедшие встречи, поиск по названию/описанию и фильтр категории. После создания организатор автоматически становится участником: лимит 2–200 включает его место. Указываются название, описание, категория, место и будущие дата/время. В браузере время локальное, в PostgreSQL — UTC.

Заявка не занимает место. Организатор видит ожидающие заявки и принимает или отклоняет их. Принятие создаёт участника только при свободном месте. При полном составе новые заявки не принимаются; старые ожидающие заявки остаются до решения организатора. Повторная отправка уже ожидающей заявки запрещена. После отклонения можно снова подать заявку; отклонение не расходует число успешных вступлений.

После первого добровольного выхода разрешены повторная заявка и второе успешное вступление. После второго выхода повторное вступление запрещено. Всего допускается два успешных вступления в каждое мероприятие. Исключение организатором требует непустую причину и навсегда закрывает вступление именно в это мероприятие. Для другого мероприятия счётчики начинаются заново. Причина видна исключённому участнику в его карточке участия и личном уведомлении, другим студентам не выдаётся. Организатор не может выйти или исключить себя.

После времени начала изменение состава закрывается; прошедшие встречи доступны для просмотра. Редактирование и удаление мероприятий в этом этапе не реализованы.

Внутри раздела есть раскрывающийся блок «Уведомления мероприятий»: новые заявки адресуются организатору, принятие/отклонение и исключение — заявителю, выход — организатору. Записи сохраняются в БД. Блок обновляется каждые 30 секунд, пока раздел открыт, и вручную. Это локальный раздел уведомлений, не общая система в верхней панели и не push/WebSocket. Непрочитанные показываются первыми, по 30 записей. После чтения показанных можно загрузить следующую порцию непрочитанных.

| `GET /api/events/:id`                                     | Детали, активный состав и собственный статус; ожидающие заявки видит только организатор |
| `POST /api/events/:id/apply`                              | Заявка на участие                                                                       |
| `POST /api/events/:id/applications/:applicationId/accept` | Принятие организатором                                                                  |
| `POST /api/events/:id/applications/:applicationId/reject` | Отклонение организатором                                                                |
| `POST /api/events/:id/leave`                              | Добровольный выход                                                                      |
| `POST /api/events/:id/members/:memberId/kick`             | Исключение: JSON-поле reason обязательно                                                |
| `GET /api/events/notices`                                 | Только собственные уведомления                                                          |
| `POST /api/events/notices/read`                           | Чтение своих уведомлений по JSON-массиву ids                                            |

Таблицы Event, EventApplication, EventMember и EventNotice добавляются отдельной миграцией поверх старой схемы. В PostgreSQL действуют уникальные ключи и CHECK-ограничения состояния и счётчиков. Обновление не сбрасывает аккаунты, интересы и сессии.

Каждое изменение состава выполняется в транзакции READ COMMITTED с блокировкой строки Event через SELECT FOR UPDATE. Это сериализует принятие, выход и исключение для одного мероприятия. Число активных участников повторно проверяется после получения блокировки; SQL-параметры не строятся из строк пользователя.

### Проверки и их ограничения

119 автоматических проверок прошли на изолированной PostgreSQL WASM-среде PGlite; TypeScript и production-сборка прошли. Среди новых сценариев — параллельные HTTP-запросы на последнее место и дублирующие заявки. **В этой среде используется одно соединение:** это не подтверждает работу блокировок между отдельными PostgreSQL-процессами. Ручная проверка интерфейса в браузере, нагрузочный тест и реальные push-уведомления не выполнялись.

Для проверки многосоединительной гонки предусмотрен отдельный режим: задайте EVENT_TEST_DATABASE_URL на специальную PostgreSQL-базу с `test` в имени и выполните `npm test`. Тест создаёт случайную отдельную схему, применяет миграции, использует пул из пяти соединений, затем удаляет только эту схему. Нужны права CREATE SCHEMA. При подготовке этот режим не запускался. Не используйте для него рабочую базу; по умолчанию никакая пользовательская PostgreSQL не затрагивается.

Основные файлы: apps/api/src/events.ts — серверные проверки и переходы состояний; apps/api/src/events.test.ts — HTTP/БД-сценарии; apps/web/src/EventsPage.tsx — лента; CreateEventPage.tsx — создание; EventDetailPage.tsx — заявки и состав; EventNotices.tsx — уведомления.

Также исправлена замеченная при регистрации подсказка пароля: проверка буквы и цифры выполняется на первом шаге, а серверная ошибка пароля возвращает на него и содержит подпись «Пароль».

## Личные сообщения и телефон (этап 5)

Кнопка «Написать» работает в карточке студента и его публичном профиле. Для каждой пары пользователей создаётся один диалог независимо от того, кто начал общение. Общение доступно только студентам колледжа с подтверждённой почтой. Поддерживается только текст — до 4000 символов; фотографии, видео и файлы не отправляются.

Раздел «Сообщения» показывает список диалогов, последнее сообщение, время и непрочитанные. Диалоги выдаются по 30, история — по 100 сообщений с подгрузкой более ранних. Последовательность определяется серверным id, время отображается в часовом поясе браузера. Enter отправляет, Shift+Enter добавляет строку. При ошибке/таймауте текст остаётся в поле; повтор использует тот же clientId и не создаёт второй экземпляр сообщения. Черновик сохраняется только в памяти текущего окна, не после обновления страницы.

Сообщение сначала фиксируется в PostgreSQL, затем сервер отправляет событие Socket.IO двум участникам. Отправка проходит по HTTP с сессией, Origin и CSRF; получение в реальном времени — через Socket.IO. Клиент не управляет комнатами, отправителем или адресатом доставки. Для входа в Socket.IO проверяются cookie, CSRF-токен, разрешённый Origin, срок сессии и подтверждение почты. Сессия повторно проверяется перед доставкой; выход и окончание сессии закрывают соединение. Сообщения не хранятся в памяти сервера как единственный источник истории.

После восстановления соединения клиент запрашивает пропущенные сообщения через `after`; при недоступном соединении обновление дополнительно выполняется каждые 15 секунд. Это не гарантия доставки Socket.IO самого по себе: источником истины остаётся сохранённая история. Сообщения отмечаются прочитанными, когда диалог открыт, окно видно и имеет фокус, а история прокручена к последним сообщениям. Курсор чтения растёт монотонно. Значок раздела учитывает непрочитанные сообщения и ожидающие входящие запросы номера; в списке диалогов запрос подписан отдельно.

### Запрос номера

В раскрывающемся блоке «Телефон и разрешения» доступна кнопка «Запросить номер», если собеседник указал телефон в профиле. Владелец видит запрос в этом диалоге и может разрешить или отклонить. Одобрение выдаёт номер только запросившему студенту. Владелец может отозвать разрешение. После отклонения или отзыва повторный запрос доступен через минуту.

Смена или удаление телефона в профиле автоматически отзывает все одобренные и ожидающие разрешения на этот номер. Старое открытое окно не может повторно одобрить новую заявку: сервер проверяет версию записи. Решения и изменение телефона используют блокировку строки владельца, чтобы не оставлять разрешение на обновлённый номер. По Socket.IO передаются только сигналы изменения разрешения, сам номер запрашивается отдельно после проверки доступа. Email собеседника через чат не раскрывается.

Отзыв закрывает последующие обращения к номеру через приложение. Он не может удалить номер, который собеседник уже запомнил или скопировал. В браузере данные телефона не помещаются в localStorage.

### API чата

Все маршруты требуют действующей сессии и подтверждённой почты. Нельзя читать, писать, отмечать прочитанным или запрашивать телефон через чужой диалог. POST дополнительно требует Origin, JSON и X-CSRF-Token. Ограничения на аккаунт: 180 изменяющих действий в минуту и отдельно 60 сообщений в минуту; ограничения хранятся в памяти одного Node.js-процесса.

## Этап 7: лента знакомств и интерфейс, 0.7.0

Раздел «Люди» сохраняет обычный каталог с фильтрами; кнопка «Лента» открывает /people/feed. Карточка показывает фото (или инициалы), имя, группу, описание и все интересы, выделяя общие. Кандидаты — другие подтверждённые студенты колледжа с интересами. Ранжирование по общим интересам происходит до выборки. Лента использует отдельную историю решений, фильтры обычного каталога на неё не действуют.

Управление: свайп пальцем/мышью, кнопки «Пропустить» и «Интересно», стрелки клавиатуры при фокусе карточки. Вертикальная прокрутка не считается свайпом. Небольшое горизонтальное движение возвращает карточку на место. Сетевое сохранение предшествует смене карточки. Ошибка оставляет возможность повторить запрос без дубликата.

Вправо (LIKE): Notification PERSON_INTEREST с именем и ссылкой /users/<отправитель>. Получатель может открыть профиль и нажать «Написать». Взаимность не требуется. В уведомлении нет телефона/почты; номер по-прежнему виден только после разрешения в диалоге. Уже отмеченный человек не возвращается в ленту; обычный каталог и профиль остаются доступны. Слева (SKIP): скрытие на 7 дней только в своей ленте, без уведомления. По истечении срока кандидат доступен снова. Это не блокировка пользователя.

Повторные/параллельные решения по той же паре не дублируют интерес. Пока пропуск активен, устаревшая вкладка не может заменить его интересом; ранее отправленный LIKE не меняется на SKIP. Действия сериализуются блокировкой строки аккаунта FOR NO KEY UPDATE, совместимой с FK при встречных интересах. Лимит 300 действий в час на аккаунт, сессия/подтверждение/CSRF обязательны.

GET /api/people/feed возвращает person, remaining, tutorialRemaining. POST /api/people/feed/:id принимает {decision:"LIKE"|"SKIP"}. POST /api/people/feed/tutorial/dismiss закрывает обучение. Счётчик обучения хранится в User, увеличивается только после нового сохранённого выбора до 2; загрузка/дубликаты/ошибки его не меняют. После первых двух карточек подсказка исчезает во всех устройствах аккаунта. Её можно закрыть раньше или открыть справку вручную. Если доступен только один другой студент, второй шаг завершится при появлении следующего.

Модели FeedChoice и feedTutorialCount введены миграцией 20261018160000_people_feed. Notification теперь допускает ровно одну цель: диалог или профиль. Существующие миграции и данные сохранены. Применять через db:generate и db:migrate, без сброса базы.

Интерфейс: адаптивная карточка, подсказки направлений на большом экране, кнопки на телефоне, светлая/тёмная тема, анимация свайпа, состояние загрузки/ошибки/пустого списка, визуальная обратная связь. Hover карточек каталога и режим prefers-reduced-motion. Зависимости не добавлены.

Проверено: 119 автоматических тестов, TypeScript и production-сборка. Среди новых проверок — приватность, права/CSRF, ранжирование, пропуск и истечение срока, доставка уведомления и профиль/чат, параллельные дубли, независимость аккаунтов, обучение и конец ленты. PostgreSQL WASM PGlite использует одно соединение; нагрузочная проверка нескольких PostgreSQL-соединений и ручная проверка жестов/дизайна в браузере/на Windows не выполнялись. Ручной чек-лист — UPDATE.md. На этап 8 автоматически не переходим.


## Этап 8: отчёты об ошибках и проверка демоверсии, 0.8.0

После входа/подтверждения ссылка внизу сайта открывает /feedback. Поля: раздел, заголовок, шаги, ожидаемое/фактическое поведение, путь страницы, необязательное устройство/браузер. Автоматически не собираются переписка, токены или подробные сведения устройства. Путь без query/hash и полного URL. Произвольный пользовательский текст остаётся текстом (React без HTML-вставок); не стоит вручную включать в отчёт пароли и чужие личные данные.

FeedbackReport хранит отчёт, автора, clientId, статус OPEN/RESOLVED, даты. Суточный лимит 10 новых отчётов проверяется в БД под блокировкой аккаунта, включая параллельные запросы. Повтор того же clientId с теми же данными возвращает исходный отчёт; с другими данными — 409. Ограничение попыток 40/час на аккаунт. Лимит БД не сбрасывается при перезапуске, лимит попыток в памяти — сбрасывается.

API: GET /api/feedback?page=1 (10 своих записей, total, page, limit); POST /api/feedback с {clientId,area,title,steps,expected,actual,page,environment}. Все маршруты требуют сессию и подтверждение почты, POST — CSRF, разрешённый Origin и JSON. Лишние поля (владелец/статус) отклоняются. Публичного просмотра чужих отчётов и управления статусами нет.

Команда npm.cmd run feedback:list из корня читает до 20 открытых отчётов; -- --status ALL --limit 50 меняет фильтр, -- --id <номер> выводит подробности. Программа использует apps/api/.env; не выводит строку подключения, email и хеши паролей. JSON-вывод экранирует управляющие символы.
